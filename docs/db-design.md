## 設計原則

1. **取引明細は CSV の写像（追記型）**。取込んだ事実をそのまま持ち、重複は業務キーで排除する。
2. **残高は「今」のスナップショット（上書き型）**。売買明細から復元できないため、現在値を表として持つ。
3. **市場データは共有、個人の値は分離**。合成は読み取りビューで行い、共有表へ個人の値を書かない。
4. **共有の外部データは「マスタ」と「キャッシュ」に分ける**。全置換するものと、持続更新するものを同じ行に載せない。
5. **派生値は保存しない**。計算で出る値はビュー（`asset_balances_view`）で導出する。

## テーブル一覧

| テーブル | 1行の意味 | 誰のもの | 誰が書くか | 消えたら再取得できるか |
|---|---|---|---|---|
| `users` | 1ユーザー | 本人 | ログイン時 | いいえ |
| `sessions` | 1ログインセッション | 本人 | ログイン時 | いいえ |
| `dividends` | 1回の配当（受取） | 本人 | CSV 取込 | いいえ（CSV が唯一の出所） |
| `domestic_stocks` | 1回の国内株式の約定 | 本人 | CSV 取込 | いいえ |
| `mutualfunds` | 1回の投資信託の約定・解約 | 本人 | CSV 取込 | いいえ |
| `asset_balances` | 1ユーザーの1銘柄の現在の保有 | 本人 | CSV 取込（上書き） | いいえ |
| `asset_balances_view` | 保有＋共有株価の合成（ビュー） | − | − | − |
| `stock` | 1銘柄（上場一覧のスナップショット） | 共有 | 週次で全置換（J-Quants） | はい |
| `security_prices` | 1銘柄の共有株価 | 共有 | 5分ごとに更新（Yahoo。1回15銘柄まで） | はい |
| `dividend_per_share_cache` | 1銘柄の1株配当＋取得状態 | 共有 | 7日で再取得（J-Quants） | はい |
| `market_data_provider_rate_control` | 上流 API の呼び出し間隔（全インスタンス共有） | 共有 | 取得時に更新 | はい |

なぜ取引が `dividends` / `domestic_stocks` / `mutualfunds` の3表なのか: 列がほぼ交わらない
（配当は税額と1株あたり、取引は約定金額と実現損益、投信は解約金額）。1表にすると
常に大半が NULL になる。

## 共有の3表（マスタ＋2キャッシュ）

`stock` / `security_prices` / `dividend_per_share_cache` はどれも「銘柄コードで1行」の共有データ。
分けている理由は **コード空間が違う** ことと、**更新の仕方が違う** ことにある。決定は
`docs/adr/0002-separate-stock-master-and-caches.md` を参照。

| | `stock`（マスタ） | `security_prices`（キャッシュ） | `dividend_per_share_cache`（キャッシュ） |
|---|---|---|---|
| コードの語彙 | 東証の4桁（J-Quants 5桁の末尾 `0` のみ＝普通株） | CSV 由来の任意コード（`SecurityCode`） | 同左 |
| 行の集合 | 上場一覧（約4,400件） | 保有 CSV に出たコード | 保有 CSV に出たコード |
| 更新 | 週1回の**全置換**（`DELETE` → `INSERT`） | 5分ごとの持続更新（1回15銘柄まで） | 7日で再取得。失敗は `stale_at` で間隔を空けて再試行 |
| 失敗時 | 上流0件なら全置換せずエラー | 前回値を残す | `status` / `error_message` を記録して再試行キューへ |
| 外部キー | 無し | 無し | 無し |

**外部キーを張らない**のは、キャッシュがマスタに無い任意コード（CSV に書かれた
存在しない・対象外のコード）を持ちうるため。先に出来て後から崩れるのではなく、
最初から成立しない。

```
stock.code ──────────────┐
                         │  同じ4桁でも意味が揃うとは限らない
security_prices.security_code ──┤  （FK でも JOIN でも結ばない）
dividend_per_share_cache.security_code ─┘
```

## 個人値と共有値の合成（#1337 の教訓）

`asset_balances` は本人 CSV の現在値を `csv_current_price` / `csv_daily_change` に持ち、
`asset_balances_view` が共有の確定値（`security_prices.price_as_of IS NOT NULL`）を優先する。
**CSV 取込は共有表へ書かない。** 以前、個人 CSV の価格が共有の確定価格を上書きする不具合があり
（#1337 / PR #1342）、この分離で直した。表を分割したこと自体が防止策なのではなく、
ビューの優先順位と `apply_close_price` の `price_as_of` ガードが防止策である。

## 意図的にやらないこと

- 共有表の `security_code` への外部キー / コードの次元表（任意コードを通すため）
- 株価・配当の履歴テーブル（1銘柄1行の現在値で足りている）
- 個人ごとの市場データの複製（共有1行に寄せた）
- 派生値（評価額・損益率）の保存（ビューで計算する）
- 上場廃止フラグ（必要になった時点で設計する。今は仮定して足さない）
