# ADR 0002: 銘柄マスタと市場データキャッシュを分離する

## Status

Accepted（2026-10-16）

## Context

`stock`（銘柄マスタ）・`security_prices`（共有株価）・`dividend_per_share_cache`
（1株配当＋取得状態）は、どれも「銘柄コードで1行・`user_id` を持たない共有データ」で、
同じ粒度に見える。1つにまとめれば表が減り、JOIN も消せるように見える。

しかし3表はコード空間が違う。`stock.code` は東証の4桁（J-Quants 5桁の末尾 `0` のみ＝
普通株）だが、キャッシュの `security_code` は CSV に書かれた任意コード
（`SecurityCode`）で、海外株・ETF・存在しないコードを含みうる。更新の仕方も違う
（`stock` は週1回の全置換、`security_prices` は5分ごとの持続更新、
`dividend_per_share_cache` は失敗を `stale_at` で間隔を空ける再試行キュー）。

独立したレビュー（Codex / OpenCode Cat Jam / big-pickle / space-bunny）で、分離と
統合の両案を比較した。詳細な議事は #1353 にある。

## Decision

3表は分離したまま維持する。スキーマの変更はしない。

- 分離の理由は **(1) コード空間が違う** ことと **(2) 更新の仕方（全置換 / 持続更新＋
  再試行キュー）が違う** ことの2点とする。
- キャッシュの `security_code` に外部キーを張らない。マスタに無い任意コードを許容する。
- 株価・配当の履歴、コードの次元表、上場廃止フラグは、必要になった時点で設計する。

## Consequences

- `stock` は「全置換」という最も単純な同期方法を保てる。キャッシュが同居しないため、
  週次の全置換がキャッシュを巻き添えにしない。
- キャッシュの失敗意味論（前回値を残す / 再試行キュー）とレート制御を、マスタに混ぜずに済む。
- 表は3つあるが、相互の JOIN も FK も存在しないため、統合で消える結合は無い。
- 後から読む人は「3表が同じ粒度に見える」ため、この文書と `docs/db-design.md` を
  先に読む必要がある。

## 却下した案

- **3表を1表に統合**: `stock` の全置換がキャッシュを消すため upsert＋上場廃止フラグが必須になり、
  マスタに無い任意コードで `GET /api/v1/stocks` の意味（属性を持つ上場一覧）が壊れる。
  週次の `DELETE`/`INSERT` と5分ごとの upsert を同じ行に載せるとロック競合を新たに作る。
- **2キャッシュだけを統合**: 取得元が別（Yahoo / J-Quants）、失敗意味論が別、
  レート制御が別（Yahoo は無し / J-Quants は共有）で、全行が両方の関心事を持つ。
  表1つ分の節約に対して列と NULL が増えるだけ。
- **コードの次元表 `securities` を新設**: コードの同一性を要求する機能が今は無い。
  CSV 由来の任意コードを維持するための upsert 経路だけが増える。
- **キャッシュへの外部キー**: 任意コードが先に出来るため最初から成立しない。
